# InnerSpacio AI Studio

**Your space, your story.** · [innerspacio.com](https://innerspacio.com/)

A design workspace for InnerSpacio's interior designers to use during client meetings: photograph a room, get an AI-assisted read on it, generate and present redesign concepts, and build a structured preliminary estimate — all without exposing internal costs or margins to the client.

This is **Phase 1**: the foundation. It runs fully in demo mode with sample data out of the box, and upgrades feature-by-feature as you add credentials.

---

## Quick start

```bash
npm install
npm run dev
```

Open [http://localhost:3000](http://localhost:3000). With no Supabase credentials set, you're dropped straight into the app — no login — with a demo-mode banner and two sample projects (a full-home job with a kids' bedroom and two bathrooms, and an empty living-room project) to explore the meeting workflow.

**If you've configured Supabase** (see below), the app requires sign-in — you'll be redirected to `/login`. There's no public sign-up; see [Authentication & initial user setup](#authentication--initial-user-setup) to create your first account.

Other commands:

```bash
npm run build         # production build
npm run start         # run the production build
npm run lint          # eslint
npm run test          # unit tests (pricing engine, auth routing, presentation DTO, ownership checks)
npm run create-user -- "email" "password"   # create a Supabase Auth account (see Authentication section)
```

## What demo mode actually does

With no environment variables set, the app is **fully interactive**, not a static mockup:

- Projects, rooms, photos, AI analyses, concepts, estimates and the cost catalogue all persist to a local JSON file (`.data/demo-db.json`, git-ignored) via the same `Repository` interface the Supabase implementation uses. Restart the dev server and your data is still there.
- Room photo uploads are stored as inline data URLs (no cloud storage) — the UI says so.
- "Analyze Room with AI" clearly explains that `ANTHROPIC_API_KEY` is missing and lets you continue the design brief manually. It **never fabricates an analysis.**
- Design concepts are generated by a `DemoImageGenerationProvider` that returns an on-brand SVG placeholder, explicitly labeled **"Demo concept — illustrative placeholder, not generated from your photo."** It never shows a stock photo as if it were a redesign of the client's room.
- No login is required, because there's no real identity provider to check credentials against in demo mode.

Configuring Supabase, Anthropic and/or an image-generation provider upgrades each piece independently — see below.

**Demo mode is for local development only.** If this app is run with `NODE_ENV=production` and Supabase is *not* configured, `proxy.ts` (the route-protection layer) deliberately blocks every request with a 503 rather than silently serving the internal dashboard to anyone who reaches the URL. Demo mode cannot be used to skip authentication in a real deployment.

### Setting up Supabase (optional, for persistence beyond this machine)

1. Create a project at [supabase.com](https://supabase.com).
2. Run the migrations, in order, via the SQL editor (or the Supabase CLI: `supabase db push`):
   - `supabase/migrations/0001_init.sql` — all core tables, RLS policies, and a private `room-photos` storage bucket.
   - `supabase/migrations/0002_presentation_links.sql` — client presentation links, client decisions/feedback, published estimate versions, and the audit event log. Required for the "Client presentation links" feature below; the rest of the app works without it.
3. Optionally run `supabase/seed.sql` for the illustrative cost catalogue and the same sample projects used in demo mode.
4. Copy the Project URL, anon key and service-role key into `.env.local`.
5. Create your first account — see the next section. The app requires sign-in as soon as Supabase is configured.
6. **Before deploying anywhere reachable by anyone other than your team:** read the [Security checklist](#security-checklist-before-deploying) below in full.

## Authentication & initial user setup

There is **no public sign-up screen** — accounts can only be created by someone who already holds the `SUPABASE_SERVICE_ROLE_KEY` (Supabase Auth's admin user-creation API requires it, and nothing else in this app does). This is intentional: the studio's client list and pricing data shouldn't be one open registration form away from a stranger's account.

**Create the first user:**

```bash
npm run create-user -- "you@yourstudio.com" "a-strong-password-min-8-chars"
```

This runs `scripts/create-user.ts`, which reads `.env.local` directly and calls Supabase Auth's admin API to create an email-confirmed user. It refuses passwords under 8 characters and a short list of obviously common ones (`password`, `admin123`, etc.) — that check is a minimum, not a substitute for your own password policy. Run it again with a different email for each additional designer.

**Signing in:** go to `/login`. Sign-in is handled by `signInAction` (`lib/actions/auth.ts`), which calls `supabase.auth.signInWithPassword` through the session-bound server client so the resulting session cookie is set correctly — never by a client-side call with the anon key directly. Invalid credentials return a generic "Invalid email or password" (the app deliberately doesn't reveal whether the email or the password was wrong).

**Signing out:** the "sign out" control in the sidebar calls `signOutAction`, which calls `supabase.auth.signOut()` (invalidating the session server-side, not just clearing a client flag) and redirects to `/login`.

**Access model:** every signed-in user currently has equal access to every project — there's no per-designer ownership (see "Deferred to Phase 2"). This matches a small boutique studio where any designer might cover any client meeting. If that stops being true for your team, see the RLS policies in the migration file — they're the place to add per-owner restrictions.

### Setting up Claude

Get an API key from the [Anthropic Console](https://console.anthropic.com/settings/keys) and set `ANTHROPIC_API_KEY`. The key is read only on the server (in `lib/ai/claude.ts`) and is never exposed to the browser or bundled into client code.

### Setting up image generation

The default `demo` provider needs nothing. To generate real concept visuals from the client's photo, set either:

- `IMAGE_GENERATION_PROVIDER=stability` and `STABILITY_API_KEY` — Stability AI's structure-preserving image-to-image endpoint, which keeps the room's architecture while restyling finishes/furniture/lighting; or
- `IMAGE_GENERATION_PROVIDER=openai` and `OPENAI_API_KEY` — OpenAI's `gpt-image-1` image-edit endpoint, used the same way (the room photo as the starting image, restyled by prompt).

To use a different provider, implement `ImageGenerationProvider` (`lib/image-gen/types.ts`) and wire it into `lib/image-gen/provider.ts` — nothing else in the app needs to change.

## Client presentation links (Phase 3)

A polished, tablet/mobile-first presentation at **`/present/[token]`** that a designer hands to a client during a meeting — no client account, no sidebar, no internal controls. Requires Supabase (migration `0002_presentation_links.sql`); there's no demo-mode version of this feature, since a real cryptographic token store and persistence are the whole point.

**Creating a link:** open a project (`/projects/[id]`) → **Client Presentation Link** panel → **Create presentation link**. The full URL is shown exactly once, in a "copy this now" banner — only its SHA-256 hash is ever stored, so it cannot be redisplayed later, including by you. If you need it again, **Regenerate** (this revokes the old one and issues a new one — the old link stops working immediately).

**Revoking a link:** the same panel → **Revoke**. The project and all past client feedback/decisions are unaffected; only the link itself stops working.

**Choosing what the client sees:** the same panel lets you check/uncheck which rooms are visible, toggle whether the project location is shown, and — per room — **Publish estimate**, which snapshots that room's current saved estimate into a versioned, client-safe copy (no base costs, no margin, no supplier rates — see "Security architecture" below). Editing the room's working estimate afterward never changes what was already published; publish again to push an update as a new version.

**Previewing:** **Preview client view** opens the exact same experience the client would see (reflecting your current visibility settings and any already-published estimate), but every action on it is disabled — nothing a designer clicks while previewing is ever recorded as a client decision. This works even before you've created a link.

**Seeing what the client did:** the same panel lists their feedback and decisions (concept selected, concept approved, estimate accepted) as they come in, each timestamped.

**On the client's side:** large original-vs-concept imagery with a draggable before/after slider, a full-screen viewer (arrow-key and swipe navigation between concepts), "select as preferred" / "approve for next stage" controls kept as distinct decisions, a feedback/change-request form, and — once published — the estimate with a clear preliminary/final label, inclusions/exclusions/assumptions and a validity period. Demo-provider concept images are labeled "Illustrative demo concept," never presented as a real AI rendering.

```
                       place every protected operation checks identity
  pricing/engine.ts    Pure, deterministic estimate calculation (+ unit tests)
  catalogue/           Illustrative seed data for the cost catalogue
  ai/claude.ts          Server-only Claude room-analysis call, Zod-validated
  image-gen/            Provider interface + demo, Stability & OpenAI impls
  data/                 Repository interface, demo (JSON file) & Supabase
                       stores (ownership checks + signed-URL refresh live here)
  presentation/
    dto.ts                The only path from internal data to the designer's
                         own /presentation view
    client-dto.ts          Allowlisted types for the token-gated /present view
  presentation-links/

    token.ts                 Resolve a token, build the client-facing DTO,
                           record decisions/feedback — the ONLY file that
                           uses the service-role key in the running app
    designer.ts               Create/revoke/regenerate/publish — session-bound
                             client, called from authenticated Server Actions
    preview.ts                 Lets a designer preview their own link's exact
                              client view without ever needing the raw token
  rate-limit.ts            Provider-neutral interface; in-memory by default
                         (NOT distributed — see its own doc comment)
  actions/               Server Actions — project/room/catalogue/settings CRUD,
                         auth.ts (sign-in/out), presentation-links.ts
                         (designer controls), presentation-client.ts (the
                         token-gated client's own decision/feedback actions)
  supabase/middleware.ts  Route-protection logic used by proxy.ts
proxy.ts               Runs before every request — auth check, demo-mode
                       production guard, /present/* rate limiting + no-store
                       headers (Next's "middleware" convention)
app/
  login/                 Sign-in page (outside the authenticated shell)
  (app)/                 Sidebar shell: dashboard, projects, design studio,
                         cost catalogue, settings — all behind login
  presentation/          Designer's own full-screen preview (no sidebar,
                         still behind login — designer's own session)
  present/[token]/        The actual client-facing link — no login, no
                         sidebar, token is the only credential
  projects/[id]/preview/  Authenticated "preview the client view" route —
                         same component as present/[token], read-only
  api/projects/[id]/rooms/[id]/{analyze,concepts,estimate}/  AI & pricing endpoints
components/present/      UI for the client-facing experience (shared by both
                       /present/[token] and the designer's preview route)
scripts/
  create-user.ts         Operator-run CLI to create a Supabase Auth account
supabase/
  migrations/
    0001_init.sql          Core schema, RLS policies, private storage bucket
    0002_presentation_links.sql  Presentation links, client decisions/
                                feedback, estimate_versions, audit log
  seed.sql                    Cost catalogue + sample projects
```

**Why Server Actions *and* API routes?** Plain CRUD (projects, rooms, catalogue, settings) uses Next.js Server Actions — they're already server-only and type-safe end to end. The three AI/pricing operations (`analyze`, `concepts`, `estimate`) are implemented as dedicated `app/api` routes with Zod-validated request bodies, because they're the operations most likely to need a stable contract, explicit HTTP status codes, and independent error handling (timeouts, rate limits, malformed AI output).

**The client presentation boundary.** `lib/presentation/dto.ts` maps a `Room`/`Project` to `ClientPresentationRoom`/`ClientPresentationProject` — types that simply don't have fields for base cost, margin, gross profit or internal notes. The presentation page can only ever render what's on that DTO; there's no cost data to accidentally leave unhidden.

**The pricing engine.** `lib/pricing/engine.ts` is a pure function with no I/O, covered by 13 unit tests (`npm run test`) including the "40% margin ≠ 40% markup" case, GST-exclusive margin calculation, and input validation (negative quantities, out-of-range percentages, division-by-zero guard when margin ≥ 100%).

## Security architecture

Three independent layers, deliberately redundant — a gap in one shouldn't mean a gap in all of them:

1. **`proxy.ts` / `lib/supabase/middleware.ts`** — runs before every request. Calls `supabase.auth.getUser()` (which revalidates the session against Supabase Auth itself, unlike `getSession()`, which only reads the cookie). Unauthenticated page requests redirect to `/login`; unauthenticated `/api/*` requests get a `401` JSON body, never a redirect (so `fetch()` callers in the UI get something they can actually handle). This is the layer that makes "don't rely on client-side navigation guards" true — there is no client-side guard; a browser with JavaScript disabled is blocked exactly the same way.
2. **Every Server Action and API route calls `requireUser()`/`getCurrentUser()` again** (`lib/auth.ts`), on top of #1. Redundant by design: if the proxy's route matcher ever has a gap, or a route is invoked in a way that bypasses it, each handler still refuses to act for an unauthenticated caller.
3. **Postgres Row-Level Security** (`supabase/migrations/0001_init.sql`) — the data layer (`lib/data/index.ts`, `lib/storage.ts`) uses the session-bound Supabase client, not the service-role client, for every normal read/write. A valid "authenticated" JWT is what RLS checks for; #1 and #2 can't be bypassed by, say, calling the Supabase REST API directly with a stolen anon key — RLS still enforces the same rule at the database itself.

**Resource-ownership checks, independent of the above.** Authentication alone doesn't stop an authenticated user from passing in a `roomId`/`photoId`/`conceptId` that belongs to a different project than the `projectId` in the URL. `SupabaseRepository` (`lib/data/supabase-store.ts`) verifies the full parent chain *before* every mutation — `assertRoomInProject()` runs first in `addRoomPhoto`, `removeRoomPhoto`, `saveRoomAnalysis`, `addConcept`, `selectConcept` and `saveEstimate`; `selectConcept` and `removeRoomPhoto` additionally verify the concept/photo itself belongs to that room, not just that the room belongs to that project. See `lib/data/supabase-store.test.ts` for the regression tests.

**Service-role key usage — the full list, nothing else:**

| Location | Why |
|---|---|
| `scripts/create-user.ts` | Supabase Auth's admin user-creation API (`auth.admin.createUser`) has no session-bound equivalent — there's no "signed-in user creates another user" concept in Supabase Auth. Run by a human operator on their own machine; never imported by, or reachable from, the running app. |
| `lib/presentation-links/token.ts` | The entire point of `/present/[token]` is that the client visiting it has **no Supabase session** — RLS cannot be satisfied any other way for that path. This is the only module in the running app that touches the service-role key, and it is the narrowest possible use of it: `resolvePresentationLink()` is the sole entry point, every other function in the file takes an *already-resolved* `PresentationLink`, and every query past that point is scoped to that link's `projectId` (see "Resource-ownership checks" below, which applies here too). `lib/presentation-links/designer.ts` and `preview.ts` — everything a signed-in designer does — stay on the ordinary session-bound client, same as the rest of the app. |

`createSupabaseAdminClient()` (`lib/supabase/server.ts`) is called from exactly one place in the running app: `lib/presentation-links/token.ts`, for the reason above. Confirm this yourself any time: `grep -rln "createSupabaseAdminClient" --include="*.ts" lib app scripts | grep -v node_modules` should only list `lib/supabase/server.ts` (its own definition), `lib/presentation-links/token.ts`, and `lib/presentation-links/token.test.ts` (which only mocks the import — it never calls a real Supabase project).

**Signed URLs for private photos.** Room photos live in a private Supabase Storage bucket (`room-photos`); nothing in it is publicly readable. A signed URL is a bearer credential independent of any session, though — whoever holds the link can view the image until it expires, logged in or not. So the app never persists a long-lived signed URL as the source of truth: `uploadRoomPhoto` only keeps `storage_path` long-term, and `SupabaseRepository.hydrateRoom` calls `refreshSignedPhotoUrl()` (`lib/storage.ts`) to mint a fresh **10-minute** signed URL every time a room is read, rather than trusting whatever was last written to the `url` column. Deleting a photo (`removeRoomPhoto`) removes the actual storage object too, not just the database row — it used to only unlink the row, leaving the file (and any link to it) live indefinitely; that's fixed.

**Client Presentation Mode (designer's own, `/presentation/[projectId]/[roomId]`).** `lib/presentation/dto.ts` is the *only* path from internal `Room`/`Project` data to anything that page can render. `ClientPresentationRoom`/`ClientPresentationProject` (`lib/types.ts`) simply have no fields for base cost, supplier rate, margin, gross profit or internal notes — there's no key to accidentally forget to strip. `lib/presentation/dto.test.ts` asserts this two ways: by listing the exact allowed top-level keys, and by seeding the input with deliberately distinctive cost/margin/note values and asserting none of them appear anywhere in the serialized output. This route is behind login — not because the client has an account, but because it's rendered on the *designer's* signed-in session, not handed to the client as a link.

**Token-gated client presentation links (`/present/[token]`).** A fundamentally different trust model from everything else in the app: the visitor has no Supabase account at all.

- **The token**: `crypto.randomBytes(32)` (256 bits of entropy), base64url-encoded (`lib/presentation-links/crypto.ts`). Shown to the designer exactly once, at creation — only its SHA-256 hash is ever written to the database (`presentation_links.token_hash`, `unique`). A database read alone — a backup, a leaked `pg_dump`, a compromised service-role key — cannot be turned back into a working link. SHA-256 (not a slow password hash like bcrypt/argon2) is the right tool here: this is hashing 256 bits of real randomness, not a guessable human password, so hash *speed* isn't the relevant property — the one-wayness is.
- **Every state the raw token touches**: generated server-side → returned once from `createPresentationLinkAction`/`regeneratePresentationLinkAction` → shown in the designer's browser in a "copy now, won't be shown again" banner → sent back by the client as a plain function argument to a Server Action on every subsequent request. Never logged (`grep -rn "console\." lib/presentation-links` shows only an unrelated audit-insert-failure log, no token), never stored beyond that one display.
- **What a resolved token actually authorizes**: nothing beyond the single `project_id` it's bound to. `recordClientDecision`/`recordClientFeedback` (`lib/presentation-links/token.ts`) re-verify the full `project → room → concept`/`estimate_version` chain on every single call — the same `assertRoomInProject`-style pattern used for the authenticated app (see above), applied again here independently, because this path doesn't get RLS's protection (it's running as service-role) and has to earn its safety entirely through this application-level scoping. `lib/presentation-links/token.test.ts` covers the resolve states (valid/expired/revoked/not-found, all collapsing to the same generic client-visible message) and the ownership-chain rejections (wrong room, wrong concept, wrong/stale estimate version) with a fake Supabase client — no real database needed to prove the logic.
- **The published-estimate table has no cost columns at all** — `estimate_versions` (migration `0002`) only has `subtotal_before_gst`, `gst_percent`, `gst_amount`, `total_client_estimate` and client-safe `line_items` (name/unit/quantity, never a rate). There is no base-cost or margin column to accidentally `select("*")` and leak; the schema itself is the allowlist. `getClientPresentationData` also simply never queries the `estimates` or `cost_catalogue_items` tables (the ones that *do* hold cost/margin data) — confirmed in `lib/presentation-links/token.test.ts`.
- **Signed photo URLs** for the client page use the same `refreshSignedPhotoUrl()` short-TTL pattern described above — regenerated on every page load, never persisted long-term.

**Rate limiting (`lib/rate-limit.ts`).** A provider-neutral `RateLimiter` interface with one implementation: an in-process, in-memory sliding-window limiter. Applied at two points: `proxy.ts` rate-limits the whole `/present/*` surface by IP (60 requests/minute) — coarse abuse/scraping protection independent of any one link; `submitClientDecisionAction`/`submitClientFeedbackAction` additionally rate-limit by the specific link (`lib/actions/presentation-client.ts`, 30/min and 10/min respectively) — so one link being spammed doesn't depend on catching it by IP. **This in-memory implementation is explicitly not distributed** — it's correct for a single long-lived Node process (e.g. this app run locally or via `next start` on one machine) and **wrong** the moment you run more than one server instance or any serverless/edge deployment, where each instance gets its own independent counter. For a real multi-instance deployment, implement `RateLimiter` against a shared store (Upstash Redis via `@upstash/ratelimit`, Vercel KV, or an atomic-increment Postgres table) and swap it in via `getRateLimiter()` — nothing else needs to change. `lib/rate-limit.test.ts` covers the limiter's own logic (allows-then-blocks, per-key isolation, window expiry); `lib/supabase/middleware.test.ts` covers it wired into the actual request path, including a real 429 after 61 requests from one IP.

**Caching.** Every response under `/present/*` gets `Cache-Control: private, no-store, no-cache, must-revalidate` from `proxy.ts` — a token-protected page must never sit in a shared/public cache (CDN, corporate proxy, etc.), since it's specific to whoever holds that one token. `export const dynamic = "force-dynamic"` on the page itself also rules out Next's own build-time static caching.

## Security checklist before deploying

Read this before pointing a real domain at a real Supabase project:

- [ ] Run `npm run create-user` for each real designer; don't reuse the `designer-test@innerspacio.local` account created during development/testing of this build.
- [ ] Rotate `SUPABASE_SERVICE_ROLE_KEY` if it was ever pasted into a chat, ticket, or anywhere outside `.env.local` / your secrets manager.
- [ ] Set real environment variables in your hosting platform's secrets store — never commit `.env.local`, and double-check `.gitignore` still covers `.env*` and `.data/` before your first push.
- [ ] Confirm `NODE_ENV=production` is actually set by your deploy pipeline — the demo-mode production guard in `proxy.ts` depends on it.
- [ ] Re-run `npx tsc --noEmit && npm run lint && npm run test && npm run build` on the exact commit you deploy.
- [ ] Review `supabase/migrations/0001_init.sql`'s RLS policies against your actual team size/trust model — as shipped, any authenticated user can read and write every project. Add per-owner (`projects.owner_id`, already a column) restrictions if that's no longer appropriate.
- [ ] Decide a password policy and communicate it — `scripts/create-user.ts` only enforces a floor (≥8 chars, not a common password), not your organization's actual requirements.
- [ ] Put the deployment behind HTTPS (required for secure cookies to actually behave securely — see "Known limitations" below).
- [ ] If you add a custom domain or email provider for Supabase Auth, set up password-reset email delivery — this build has no "forgot password" flow; resetting currently means re-running `create-user` is not possible for an *existing* email (admin API will error), so use the Supabase dashboard's Auth → Users panel to reset a password directly if needed.
- [ ] **If you'll run more than one server instance** (multiple containers, serverless/edge, autoscaling) — replace `lib/rate-limit.ts`'s in-memory limiter with one backed by a shared store before relying on the `/present/*` rate limits for anything. The in-memory version silently becomes `limit × instance count` across multiple processes.
- [ ] Revoke any presentation links created during testing (`designer-test@innerspacio.local`'s project, or any test project) before they'd be mistaken for a real client-facing link.

## Known limitations — not resolved, or not verifiable locally

Reported plainly, as asked:

- **No rate limiting on `/login`.** `signInAction` returns a generic error on failure (doesn't leak which field was wrong), but nothing here throttles repeated attempts. Supabase Auth has its own backend rate limits, which this app doesn't configure or control — review them in your Supabase project's Auth settings before relying on them.
- **No password-reset / "forgot password" flow.** Noted above; out of scope for this pass.
- **Cookie security flags couldn't be verified end-to-end locally.** `@supabase/ssr` sets the session cookie with `Secure` in a context that supports it, but `http://localhost` is not a secure context, so this was not something I could observe directly in this environment — it needs verification once this runs under a real HTTPS origin.
- **No automated test exercises the real Supabase-backed HTTP stack** (login → cookie → protected page → RLS-filtered data) end-to-end in CI — that full path was verified manually in this session (direct `supabase-js` sign-in + RLS check, then the actual `/login` UI through a browser, including confirming logout invalidates the session rather than just redirecting). The automated test suite covers the pieces that can be unit-tested in isolation (middleware routing logic with mocked auth state, repository-level ownership checks with a fake Supabase client, the presentation DTO) — see `npm run test`.
- **Single trust tier.** As stated above, there's no per-designer data isolation — every authenticated account can read/write every project. This is a deliberate scope decision matching a small single-team studio, not an oversight, but it means a compromised account (not just a compromised unauthenticated request) has full access.
- **No audit log** for the *internal* app (project/catalogue/settings edits) beyond each table's `updated_at` — the Phase 3 `presentation_audit_events` log only covers the client-presentation-link surface (link created/revoked, client viewed/selected/approved/accepted/left feedback), not internal CRUD.
- **Supabase project-level settings weren't reviewed as part of this pass** (e.g. email confirmation requirements, session/JWT expiry length, MFA availability) — those live in the Supabase dashboard, not this codebase, and are worth a deliberate look before launch.
- **The in-memory rate limiter is not distributed** — repeated for emphasis because it's the limitation most likely to silently stop mattering in production: correct for one process, wrong for more than one. See the checklist above and `lib/rate-limit.ts`'s own doc comment.
- **No end-to-end test of the real token flow against a live Supabase project** — `lib/presentation-links/token.test.ts` proves the resolve/ownership logic against a fake Supabase client (no network), which is what's practical in an automated suite; the actual migration, RLS policies and live data path need a manual pass against your real project (steps are in the final report / "How to test locally" below) before you trust this in front of a real client.
- **The before/after slider and full-screen viewer were built and type-checked but not verified on a physical tablet or phone** in this session — only via responsive breakpoints in the code and (where noted below) a desktop browser at narrowed viewport widths. Do a hands-on pass on an actual iPad/Android tablet before a real client meeting.

## Implemented in Phase 1

- Premium dashboard with live counts (projects, in-progress, concepts awaiting selection, estimates prepared) and recent-projects list.
- Full project CRUD: client details, location, status, budget range, preferences, notes. Projects save with partial information.
- Multiple rooms per project, each with dimensions (length/width/ceiling height, ft or m), existing-condition notes, style/palette/storage/material preferences, per-room budget, and constraints.

## Implemented in Phase 3

- **Token-gated client presentation links** (`/present/[token]`) — cryptographically random (256-bit), only the SHA-256 hash ever persisted, with expiry, revocation and regeneration. See "Client presentation links" and "Security architecture" above.
- **A premium, tablet/mobile-first client experience**: large original-vs-concept imagery, a draggable (and keyboard-operable) before/after comparison slider, a full-screen viewer with arrow-key/swipe navigation, distinct "select as preferred" / "approve for next stage" client decisions, a feedback/change-request form, and a client-facing published estimate with preliminary/final status, inclusions/exclusions/assumptions and a validity period.
- **Versioned, designer-published estimates** (`estimate_versions`) — the client only ever sees a snapshot the designer explicitly published; editing the live working estimate afterward never changes what a client already saw or accepted. The schema itself has no cost/margin columns to leak.
- **Designer controls** inside the authenticated app (new panel on each project page): create/revoke/regenerate the link, choose which rooms are client-visible, publish a room's estimate, preview the exact client experience in a read-only mode (works even without an active link, and without ever needing the raw token again), and see client feedback/decisions as they arrive.
- **Provider-neutral rate limiting** (`lib/rate-limit.ts`) on token resolution (by IP) and client write actions (by link) — shipped with an honestly-documented in-memory implementation, not claimed as distributed.
- **Private, no-store caching** on the entire `/present/*` surface.
- 24 additional passing unit tests (51 total) covering token resolve states, cross-project/cross-room ownership isolation, rate-limiter behavior wired into the real request path, and structural proof that the client-facing data path never touches the tables that hold cost/margin data.

## Deferred

- **PDF export** of either presentation surface (print-to-PDF via the browser works today; a dedicated export endpoint does not).
- **Additional image-generation providers** beyond the demo, Stability AI and OpenAI implementations (e.g. a provider with inpainting/masking for finer control).
- **Multi-user / per-designer ownership** — RLS currently grants any authenticated user access to all studio data, appropriate for a small team but not fine-grained (see "Known limitations" above).
- **Password reset / "forgot password" flow**, rate limiting tuned specifically for the internal app's login, and an audit log for internal (non-presentation-link) actions — see "Known limitations" above.
- **Real-time collaboration** (e.g. two designers editing the same project simultaneously) — not addressed; last write wins.
- **GST treatment configuration beyond a flat rate** — the engine calculates GST on the selling subtotal at a single configurable rate; different supply/contract structures (e.g. works contract vs. composite supply) need sign-off from your tax adviser and may need a different calculation path later.
- **A distributed rate-limiting backend** — see "Known limitations" and the checklist above; required before trusting the `/present/*` limits in a multi-instance deployment.
- **Multiple presentation links per project** (e.g. different links with different room visibility for different stakeholders) — the schema enforces at most one active link per project by design; revisit if that stops fitting how the studio actually works.
